## SUMMARY
Research for the novalis Kanban data model, read-only. Old novalis identifies notes purely by vault-relative path (note_meta PRIMARY KEY path; NoteSummary.path) and resolves [[wikilinks]] by title/alias, case-insensitive; none of the 63 demo-vault notes carries an id in frontmatter, and move_note does not rewrite links in other notes. Old novalis already keeps synced per-vault config in <vault>/.novalis/config.json, but its own P2P sync manifest (is_syncable_rel) and its file watcher both SKIP every dot-path, and its conflict-copy detector only matches *.md — three facts that shape where board data may safely live. Prior art verified: Obsidian Kanban = one Markdown file per board, '## heading' lanes, '- [ ]' cards, no stable card ids (runtime generateInstanceId), order = list order; Trello = float 'pos' (string|number); Vikunja = float64 Position with rebalance when spacing < 0.01 over a 2^32 range; Nextcloud Deck and Kanboard = integer order/position; Focalboard = explicit cardOrder: string[] on the view block; GitHub Projects v2 = relative 'afterId' placement only; beads (AI-agent issue tracker) = one JSON object per line with hash ids 'bd-a1b2' chosen explicitly to avoid merge collisions. SQLite's own docs say background sync/backup tools copying a db mid-transaction or without its -wal file corrupt it, so SQLite is rejected for the synced store (fine as a local cache, the old app's pattern). Recommendation: one directory per board inside the vault in a VISIBLE folder (boards/<slug>/board.json + cards/<ULID>.json), column membership and a fractional-index 'order' string stored ON the card so a move touches exactly one small file; two devices editing different cards offline then never collide in any sync client. Card links to notes by the same target string a [[wikilink]] would use (title or folder/title), resolved by the app's note resolver; no id is written into notes. Same-card offline edits: whole-card last-writer-wins by 'updated' (RFC 3339 UTC ms), loser preserved under boards/<slug>/conflicts/, one-line notice. Google Drive for desktop's policy on dot-folders could NOT be verified (iCloud and Obsidian Sync are reported to skip them), which is the main reason for a visible folder. WebSearch and WebFetch were available and used; crates.io was queried via curl for current versions (ulid 3.0.0, uuid 1.26.0 with v7, fractional_index 2.0.2, automerge 0.11.0, loro 1.13.9, yrs 0.27.4, serde_yaml 0.9.34+deprecated).

### F8. SQLite in a synced folder is a documented corruption risk  [verified]
sqlite.org howtocorrupt §1.2: background backups copying mid-transaction yield a corrupt copy; 'it is important that any rollback journal or write-ahead log be copied together with the database file'; §1.4 'Copying a database file without also copying its journal' likely leads to corruption; §2.1 broken locking on network filesystems. Cloud sync clients copy files independently and asynchronously, so db + -wal can be captured inconsistently. Old novalis keeps its SQLite index in app-data, never synced (WAL, busy_timeout 5s, synchronous=NORMAL) — the right pattern for a CACHE of the board files.

### F11. Fractional indexing: the rocicorp scheme and the tie-break caveat  [verified]
rocicorp/fractional-indexing: generateKeyBetween(a, b) / generateNKeysBetween(a, b, n); base-62 digits '0-9A-Za-z' with an integer-part head so keys like 'a0', 'a1', 'Zz' sort by plain byte comparison (NOT localeCompare); keys grow only when inserting between neighbours; README lists jittered variants because two clients inserting into the same gap produce the SAME key. Figma: arbitrary-precision base-95 strings, midpoint insertion, server assigns a unique position on collision, length growth 'isn't a concern' at kanban scales. Rust: crate fractional_index 2.0.2 (2024-09-17) — byte-string FractionalIndex with new_before/new_after/new_between, serde as bytes or hex via #[serde(with='fractional_index::stringify')]; no crates.io port of the rocicorp base-62 format exists (crates.io 'fractional-indexing' -> not found). Sanity check: ['Zz','a0','a0V','a1','a1V','a2'] sorts correctly bytewise.
_evidence: https://raw.githubusercontent.com/rocicorp/fractional-indexing/main/README.md ; https://www.figma.com/blog/realtime-editing-of-ordered-sequences/ ; https://raw.githubusercontent.com/drifting-in-space/fractional_index/main/README.md ; curl https://crates.io/api/v1/crates/fractional-indexing -> no crate; python sort check in scratchpad_

### F12. Stable ids: ULID vs UUIDv7, crate status  [verified]
ULID spec: 26-char Crockford base32 (no I,L,O,U), 48-bit ms timestamp + 80 bits randomness, lexicographically sortable, monotonic within a ms by incrementing the random part. RFC 9562 UUIDv7: 48-bit ms timestamp + ver + 12 bit rand_a + var + 62 bit rand_b, 'SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6', three monotonicity methods; canonical text form is 36 chars with hyphens. crates.io: ulid 3.0.0 (2026-07-16); uuid 1.26.0 (2026-08-26) with features v1,v3,v4,v5,v6,v7,v8; old novalis workspace pins uuid = '1' features ['v4'] and uses Uuid::new_v4 for its own ids. beads (Yegge, Oct 2025) uses short hash ids 'bd-a1b2' explicitly to 'prevent merge collisions in multi-agent/multi-branch workflows' and keeps issues.jsonl as an export, Dolt as source of truth.
_evidence: https://github.com/ulid/spec ; https://www.rfc-editor.org/rfc/rfc9562.html ; curl crates.io API for ulid, uuid (1.18.1 feature list), /Users/sgrundhoefer/Projects/novalis/Cargo.toml line 23 ; https://raw.githubusercontent.com/steveyegge/beads/main/README.md_

### F15. Recommended card→note linking: wikilink target string, no note modification, app-side rename repair  [likely]
Three options: (1) stable note id in frontmatter — most robust but writes an 'id' key into every linked note (touches note files, alters Obsidian-visible frontmatter) -> owner decision; (2) vault-relative path — unambiguous, agent-friendly, breaks on any move/rename unless the app rewrites card files; (3) the same target string a [[wikilink]] uses (title, or 'folder/title' when ambiguous) — path-move-proof, breaks only on title change, and the editor's own link-rename logic (if built) covers cards and note bodies in one place; matches old novalis resolution semantics. Recommend (3). Renames: when the app renames/moves a note it rewrites affected card files in the same operation; externally renamed notes show the card link as 'missing' with a relink action (identical to a dangling [[link]]). Reverse direction: never stored in the note; derived from a local index table card_links(board, card_id, target) rebuilt from card files, surfaced in the note's backlinks panel (UI = owner decision).
_evidence: Old resolver semantics: /Users/sgrundhoefer/Projects/novalis/crates/novalis-core/src/notes/mod.rs lines 376-385; index/links.rs; owner brief 'content lives OUTSIDE the notes'_

## RECOMMENDATIONS

### R1. Storage layout (b): one directory per board, one JSON file per card, one small board.json for name + columns. Path: <vault>/boards/<board-slug>/board.json and <vault>/boards/<board-slug>/cards/<ULID>.json. Column membership ('column') and position ('order') live ON the card so a drag touches exactly one ~300-byte file; board.json changes only when columns change. Pretty-printed JSON, sorted keys, trailing newline, atomic temp+rename writes (reuse the old write_atomic pattern; temp name must never be '.lock').
Only layout where two devices editing different cards offline produce zero conflicts in every sync client (each card is its own file), while remaining cat/jq-editable for AI agents, git-diff friendly (one file per change) and simple. Mirrors Focalboard's block-per-record and beads' record-per-line thinking without their databases.
_rejected: (a) single JSON per board: every edit rewrites one file, so any concurrent offline edit yields a provider conflict copy the app must detect (naming differs per provider, Google's is undocumented) and merge. (c) Obsidian-style Markdown: no stable ids, no timestamps, whole-file rewrites; cannot be merged deterministically; would also look like a note to any Markdown tool. (d) SQLite in the synced folder: sqlite.org documents corruption when sync tools copy db/-wal inconsistently; not human-readable. (e) per-device JSONL event logs and (f) automerge/loro/yrs CRDT docs merge better than (b) only for same-card edits, at a large cost in readability, agent-editability and code — flagged as future options if the in-app sync engine needs sub-card merging._

### R2. Card identity: ULID (26 chars, Crockford base32) generated on creation, used as the file name. Column identity: stable slug id chosen at column creation (e.g. 'todo'), display name separate — exactly the old KanbanColumnDef{id,title} shape. Board identity: the folder slug.
ULIDs are filesystem-safe on OneDrive/Google Drive (no forbidden chars, no hyphens), time-sortable (cards/ listing is creation order for free), collision-free across devices without coordination, and shorter than UUIDv7's 36 chars. Stable column ids mean renaming a column rewrites board.json only, never the cards.
_rejected: UUIDv7 is equally fine and would reuse the existing uuid crate (1.26.0 has v7) — acceptable if the team prefers one id crate; short hash ids (beads 'bd-a1b2') are nicer to type but need a collision-check step. Sequential integers are rejected: two offline devices would mint the same number._

### R3. Ordering: a fractional-index string per card ('order', rocicorp base-62 scheme, keys like 'a0', 'a0V', 'a1'), compared bytewise; sort within a column by (order, id). Ties (two devices inserting into the same gap) resolve deterministically by id; the app re-keys the loser on its next own write. Port generateKeyBetween/generateNKeysBetween (~150 lines) rather than adopting the fractional_index crate's hex byte-strings, so agents can read and hand-write keys.
A move changes one card file only. Integer order (Deck, Kanboard) renumbers neighbours = many files = conflicts; an order array in board.json (Focalboard cardOrder) makes every move a board-file conflict; float pos (Trello, Vikunja) needs periodic rebalancing that rewrites many cards. String keys never need rebalancing at kanban scale (Figma's experience).
_rejected: Integer order, order array, float pos — see rationale. Jittered keys avoid ties probabilistically but make keys ugly for humans/agents; the id tie-break is deterministic and free._

### R4. Minimal card schema: id, title, column, order, notes (array of wikilink target strings), created, updated (RFC 3339 UTC with ms, e.g. 2026-09-05T08:41:12.345Z). 'created'/'updated' are required for the merge rule, not optional extras. Example cards/01K4G9Z2Q7M3N8RSTV5WXY6ZAB.json: {"id":"01K4G9Z2Q7M3N8RSTV5WXY6ZAB","title":"Decide zoom bands for offline bundles","column":"doing","order":"a0V","notes":["Atlas Rendering Spec","Atlas Offline Bundles"],"created":"2026-09-01T07:12:03.010Z","updated":"2026-09-05T08:41:12.345Z"}. Unknown keys must round-trip untouched (serde flatten extra), so a later field or an agent-added key is never dropped.
This is the smallest set that renders a board, links notes and merges deterministically. Every further field is listed under owner decisions.
_rejected: Storing description/due/tags now 'because cheap' contradicts the owner's ask-first rule; a card as Markdown+frontmatter (cards/<ulid>.md) is more readable but would be indexed as a note by novalis itself, Obsidian and any grep-based agent workflow — rejected unless the owner prefers it._

### R5. Minimal board.json: {"format":1,"name":"Atlas","columns":[{"id":"todo","name":"To Do"},{"id":"doing","name":"Doing"},{"id":"done","name":"Done"}],"updated":"2026-09-05T08:41:12.345Z"}. 'Configurable' in v1 = board name + column list (add/rename/reorder/delete). A card whose 'column' no longer exists is shown in the first column with a 'column missing' marker rather than hidden (deterministic, nothing lost).
Column names/order are the only configuration a kanban cannot work without. Board renames change one string; column renames change one array entry; neither touches cards.
_rejected: WIP limits, colors, per-column 'done' semantics, swimlanes, card templates, default column for new cards — all deferred to owner decisions._

### R6. Location: inside the vault in a VISIBLE folder ('boards/'), not under '.novalis/'. Exclude '*/board.json' and 'boards/*/cards/*.json' from the note index by folder/extension rule; show each board folder as a single 'board' item in the file tree (same treatment old novalis gave '.canvas' files, whose own doc example is 'boards/plan.canvas'). Keep '.novalis/' for per-vault preferences only.
Every mechanism then carries the boards: OneDrive/Google Drive local folders (dot-folder policy unverifiable for Google, reported off for iCloud and Obsidian Sync), git, and the old P2P engine whose is_syncable_rel() rejects dot-paths; the old watcher also skips dot-folders. Boards travel with the vault under one sync story instead of two.
_rejected: '.novalis/boards/': hidden from Finder/agents by default, excluded by the old sync manifest and watcher, and dependent on an unverified provider policy. A separate synced folder outside the vault: two sync roots, two failure modes, relinking across roots._

### R7. Conflict story and deterministic merge: (1) Different cards edited offline -> no conflict by construction. (2) Same card edited on both devices offline -> the sync client leaves 'cards/<id>.json' plus a sibling copy ('<id>-<COMPUTER>.json', '<id> (1).json', "<id> (X's conflicted copy).json", Google: name undocumented — detect generically as any extra file in cards/ whose parsed 'id' equals an existing card's id). Rule: whole-card last-writer-wins on 'updated' (ms precision), tie -> lexicographically larger file content wins; the losing version is moved to boards/<slug>/conflicts/<id>-<updated>.json, never deleted; one-line, non-modal notice 'Board Atlas: 1 card had conflicting edits, kept the newer one (14:02); older copy under conflicts/'. (3) board.json edited on both devices -> same rule on 'updated'; columns present in either version are unioned so no card becomes orphaned. (4) Deletion vs concurrent edit -> with hard delete the sync client may resurrect the card; recommend a 'deleted' timestamp tombstone (owner decision) purged after 30 days. Extend the old conflict regexes to any extension, not just .md.
Whole-card LWW needs no extra per-field metadata, is fully deterministic on both devices (they converge without talking), and never silently discards data because the loser is kept on disk (Rule 5: fail loud).
_rejected: Per-field LWW requires per-field timestamps (or a CRDT) on every card for a window that only opens when the same card is edited on two offline devices; 3-way merge against a stored base needs an in-app sync engine with base manifests (the old sync/manifest.rs shape) — reasonable later, too much for v1._

### R8. Local cache: rebuild a SQLite table set (boards, cards, card_links) in app-data from the files on open and on watcher events, exactly like the old note index (WAL, busy_timeout, drop-and-rebuild on schema bump). Never sync it. Backlinks panel of a note can then list linking cards with zero writes to the note.
Keeps reads O(1) for the UI and gives the reverse link direction for free while the files stay the single source of truth.
_rejected: Storing 'cards: [...]' inside note frontmatter — violates 'content lives outside the notes'._

### R9. CLI surface for agents (later): 'novalis board list', 'novalis card add <board> --column todo --note "Atlas Overview" "Title"', 'novalis card move <id> --column doing [--after <id>]', 'novalis card link <id> "Note Title"'. Agents may also write card files directly; the CLI exists mainly to compute 'order' keys and fresh ULIDs correctly.
Matches the brief's 'AI agents via a CLI tool' and beads' lesson that agents need an id/ordering helper more than a database.
_rejected: Requiring the CLI for every edit — the files must stay editable with plain tools._

## OWNER DECISIONS
- Card fields beyond id/title/column/order/notes/created/updated: description (Markdown string)? due date? tags? color? checklist? archived/done flag? Each is a schema addition; recommendation is to ship none in v1 and add 'description' first if anything.
- Soft-delete tombstone field 'deleted' (recommended, purged after ~30 days) vs hard delete of the card file (simpler, but a concurrently edited card can be resurrected by the sync client).
- Board configuration beyond name + columns: WIP limits per column, column colors, a 'done' column semantic (auto-complete), swimlanes, multiple boards per vault (the layout supports it at zero cost — confirm it is wanted), default column for new cards.
- Note linking scheme: recommended wikilink-target strings with no note modification. Alternative: write a stable 'id' into each linked note's frontmatter (most robust to renames, but touches note files and adds a visible frontmatter key).
- Should a note's backlinks panel show 'cards linking here' (UI feature, data is free from the local index)?
- Location confirmation: visible '<vault>/boards/' (recommended) vs hidden '.novalis/boards/'. If hidden is preferred, the Google Drive / OneDrive dot-folder behaviour must be tested on the owner's machines first.
- File format: JSON (recommended) vs YAML (serde_yaml is deprecated; serde_yml 0.0.13 is the fork) vs Markdown+frontmatter per card (readable but indistinguishable from notes for other tools).
- Conflict UX: one-line notice + conflicts/ folder (recommended) vs a diff/choose dialog like the old ConflictDiff resolver.
- Id format: ULID (recommended) vs UUIDv7 (reuses the uuid crate already in the old workspace).
