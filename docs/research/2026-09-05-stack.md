## SUMMARY
Researched four stack options (Tauri+CodeMirror 6, native Swift, Rust-native GUIs, Electron) plus the editor-engine question, using WebSearch/WebFetch, crates.io/npm registry APIs, GitHub API (gh) and local build experiments in the scratchpad. Two facts in the brief are wrong for this machine and matter a lot: (1) a full Xcode 26.6 (build 17F113, first-launch complete, Metal toolchain downloaded, notarytool/actool/ibtool/xcstringstool present) IS installed at /Applications/Xcode.app — xcode-select merely points at the CLT, and DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer activates it without sudo; (2) under CLT-only, `swift test` is impossible (no XCTest.framework, no Swift Testing module — verified) and gpui 0.2.2 fails to build (`xcrun: unable to find utility "metal"` — verified), while SwiftUI/AppKit executables, ad-hoc codesign, notarytool 1.1.2 and stapler DO work under CLT. Only an "Apple Development" identity exists — no "Developer ID Application" cert, so notarized distribution needs the paid ($99/yr) Apple Developer Program. I measured hidden-window hello-worlds on this Mac (N=3, RSS via ps, release builds): SwiftUI+AppKit+NSTextView(TextKit 2): 98–115 ms to didFinishLaunching, 51 MB → 82 MB RSS after 1.5 s idle, 72 KB binary; gpui 0.2.2: 105 ms (268 ms first cold run), 57 → 62 MB RSS, 5.3 MB binary, 1m01s clean build of 403 crates; Tauri 2.11.5 with static HTML: 166–231 ms to setup(), main process 85 → 97 MB plus WebKit helpers (WebContent ~32 MB, GPU ~31 MB, Networking ~16 MB) ≈ 176 MB summed RSS, 6.3 MB binary. Electron is rejected with published numbers (244 MiB vs 8.6 MiB bundle; 409 MB vs 172 MB for 6 windows), with the honest caveat from tauri#5889 that WKWebView can exceed Chromium on heavy web apps. On text editing: NSTextView has no real multi-cursor (typing hits only the first range) and TextKit 2 silently falls back to TextKit 1; the only multi-cursor TextKit-2 view (STTextView 2.4.0) is GPL-3.0-or-commercial; Zed's editor crate is GPL-3.0-or-later and unpublished; gpui-component 0.6.0 (2026-09-03, Apache-2.0) ships a tree-sitter code editor but no Markdown live preview; iced 0.14 and floem have zero AccessKit code; egui still lacks HarfBuzz shaping (Parley port is a WIP PR); gpui gained AccessKit a11y in May–Jul 2026 and has NSTextInputClient IME. CodeMirror 6 (@codemirror/view 6.43.11, 2026-09-03) verifiably has multi-cursor (allowMultipleSelections, rectangularSelection, selectNextOccurrence), search/replace, Decoration.replace/widget incl. block widgets, Lezer grammars for markdown/yaml/json (+ TOML via legacy-modes; no CSV mode), 'few million lines' demo, and 2025–26 changelog fixes for Safari 26 and dead-key composition. Recommendation: Option A — Tauri 2.11 + CodeMirror 6 source-mode Markdown with live decorations (Obsidian-style), Rust core crate shared with the CLI, ~70% confidence; fallback C (gpui-pre 0.3.x + gpui-component 0.6) if a two-week spike shows WKWebView cannot hit typing-latency/50 MB targets; Option B only if macOS-only-forever is acceptable.

### F14. Editor engine — TextKit 2 vs CodeMirror for 'text editor first' feel  [likely]
CodeMirror 6 is the only engine that (a) is built as a code/text editor first, (b) has multi-cursor, column selection, find/replace, folding, bracket matching out of the box, (c) has a Markdown grammar with per-node syntax tree usable for cursor-aware decorations (hide `**` when cursor leaves the line, render headings/links/checkboxes inline), (d) inherits native macOS text input/IME/dead keys/spellcheck/VoiceOver from WebKit. TextKit 2 gives the most native feel but no multi-cursor, fallback traps and immature third-party views; gpui-component's code editor is the strongest native alternative but has no Markdown live preview and is 2 days old at 0.6.0. Verdict: CodeMirror 6 for editor-first with Markdown niceties; Lezer (not tree-sitter/wasm) as the highlighter in the web stack — tree-sitter only for the Rust core/CLI (outline, wikilinks, tasks) if needed.
_evidence: Synthesis of the verified items above_

### R1. Choose Option A: Tauri 2.11 (Rust core crate shared with the CLI) + CodeMirror 6 as the one editor engine (source-mode Markdown with cursor-aware live decorations, Lezer grammars for md/yaml/json/toml; plain text/csv/code via CM6 language packs). Confidence ~70%.
It is the only stack where 'text editor first with Markdown niceties' is a proven pattern (Obsidian Live Preview is CM6), where IME/dead keys/umlauts/spellcheck/VoiceOver come for free from WKWebView, where the CLI and app share one Rust crate in-process, where later Windows/Linux is possible, and where coding agents get HMR + vitest + typed IPC. Measured cost vs native on this Mac is ~2x memory (≈176 MB summed vs 62–82 MB) and ~70–120 ms extra startup — still 'instant' and far below Electron. The team already knows this stack (old novalis). Top 3 risks: (1) 10–50 MB files inside WebKit — JS string + Lezer tree memory and IPC JSON cost; mitigate with ipc::Response/raw file reads, a size threshold (~5 MB) that disables Markdown decorations/highlighting, and a week-1 spike opening a 50 MB file; (2) the live-preview extension has no mature library (35★/136★ references) — budget 2–4 weeks in-house and keep it optional per owner decision; (3) WKWebView/Tauri platform quirks — WebKit version tied to min macOS, drag&drop issues (#9966/#14624/#14643), Safari composition edge cases (CM6 ships workarounds). Fallback: Option C with gpui-pre 0.3.x + gpui-component 0.6 code editor (62 MB, 105 ms, single language) if the spike fails typing-latency or large-file targets — accepting pre-1.0 churn and building Markdown preview from scratch; Option B only if the owner drops the 'other platforms later' goal.
_rejected: B Swift/AppKit: fastest/lightest native feel but macOS-only forever, NSTextView has no real multi-cursor, TextKit 2 fallback traps, STTextView is GPL-or-commercial, CodeEdit views not production-ready, tests need Xcode toolchain, FFI to Rust core. C gpui: best numbers and Rust-only, but pre-1.0 breaking changes, thin docs, Xcode Metal at build (or untested runtime_shaders), Zed's editor is GPL and unpublished, no Markdown preview component, accessibility maturity unverified. Other Rust GUIs: egui (no shaping/ligatures, TextEdit not for large docs), iced/floem (no accessibility), slint (GPL/attribution license, basic multiline input), makepad/xilem (immature). D Electron: 244 MiB bundle, 2–3x RAM, no in-process Rust core._

### R2. Keep the frontend framework decision minimal and separate from the editor: CM6 is framework-agnostic; use React 19 only if @novalis/ui components are reused, otherwise prefer vanilla TS or Solid for the shell (sidebar, Kanban). Needs owner decision.
The editor is the performance-critical part and lives outside any framework. A lighter shell reduces WebContent memory and startup, but React has team/agent familiarity and existing i18next tooling. I did not verify Solid/Svelte versions in this session.
_rejected: Monaco (93 MB, VS Code-shaped, cannot cleanly hide ranges for inline Markdown rendering); TipTap/ProseMirror (WYSIWYG, lossy Markdown round-trip, no multi-cursor, contradicts 'text editor first')._

### R3. Toolchain policy on this machine: set DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer in scripts/CI-like tasks (no sudo needed) so `swift test`, Metal and xcstringstool work when needed; keep Tauri builds on the plain CLT path (cargo tauri build + codesign + notarytool + stapler all present). Obtain a Developer ID Application certificate (paid program) before the first notarized release.
Verified: CLT alone cannot run Swift tests or compile Metal; the installed Xcode fixes both without changing xcode-select. Only an Apple Development identity exists today, so notarization is currently impossible.
_rejected: Installing swift-bundler (Apache-2.0, last tagged release v2.0.4 from 2022, install from @main, no notarytool integration found) is unnecessary for Option A; for Option B a 30-line Info.plist+codesign script suffices._

### R4. Adopt an explicit large-file policy as a product rule (not a setting): above a byte threshold (e.g. 5 MB) open in plain-text mode with Markdown decorations and syntax highlighting off; above ~50 MB warn. Needs owner decision on the thresholds.
Both Zed (issue #4701) and Obsidian users hit degradation with huge files; CM6 parser already self-limits, but WebKit process memory pressure is real (tauri#5889). A rule avoids adding a user-facing setting, matching the owner's minimalism.
_rejected: Custom rope editor to guarantee 50 MB editing — months of work for IME/bidi/a11y parity._
