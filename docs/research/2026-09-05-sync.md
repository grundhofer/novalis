# sync

TOOLS: WebSearch and WebFetch were available and used extensively (Google/Microsoft/Apple docs fetched directly; Apple's TN3150 via its JSON data endpoint because the HTML page is JS-rendered). Bash was used to read old novalis sources, download and parse the Drive v3 discovery JSON with curl/python3, inspect the SDK headers, stat/xattr the real OneDrive File Provider folder on this Mac, and compile+run C and Rust probes for SF_DATALESS/setiopolicy_np/EDEADLK. Not used: the Google Drive MCP tool (only an authenticate action was exposed) and the Chrome browser tools. No files outside the scratchpad were modified; the probes performed only metadata reads and a policy-blocked read on two existing dataless files (which stayed dataless).

## SUMMARY
Research covered both sync modes with a mix of live doc fetches, vendor discovery/JSON endpoints, and hands-on tests on this Mac (which has a real OneDrive File Provider domain at ~/Library/CloudStorage/OneDrive-Persönlich containing two dataless files; Google Drive is not installed here). MODE 1 is technically solid and cheap: dataless files are reliably detected via st_flags & SF_DATALESS (Rust std exposes st_flags on macOS; verified compile+run on rustc 1.96), the old novalis st_blocks heuristic agrees with the flag on every file checked, stat() does not materialize, and setiopolicy_np(...OFF) on the scanning thread makes read() fail with EDEADLK instead of downloading (verified locally; the libc crate does not expose the call, a 1-line extern "C" is needed). Unverified in Mode 1: FSEvents delivery semantics inside CloudStorage, whether temp+rename saves are problematic for File Provider, and the exact vendor conflict-copy naming (OneDrive '<name>-<ComputerName>' is consistent across community sources; Google Drive for desktop naming has no official doc). MODE 2 Google: use drive.file (non-sensitive, per-app folder) to avoid the restricted 'drive' scope and its annual CASA (~$540–$4,500); Drive v3 has NO etag/If-Match (discovery doc rev 20260901 verified) so conflict control is check-then-write on the monotonic 'version' field plus server md5/sha256 checksums; changes.list tokens never expire; Google Desktop-type clients in practice need the client_secret at token exchange, which Google's own docs say is 'obviously not treated as a secret' for installed apps. MODE 2 OneDrive: Graph is the better sync substrate — delta with 410 resync semantics, upload sessions with If-Match/412 (true compare-and-swap on cTag), quickXorHash as the only hash guaranteed for personal+business, refresh tokens rotate and last 90 days; 'Mobile and desktop applications' platform with http://localhost (port ignored) and PKCE, no secret. Publisher verification requires a Partner Center account and a work/school tenant; without it only personal accounts and tenants without step-up consent can consent. Design recommendation for Mode 2: reuse the old novalis pure 3-way planner (novalis_core::sync::manifest plan/next_base) and OAuth loopback code (apps/desktop/src-tauri/src/oauth.rs), add a SQLite state DB + content-addressed base blobs, auto 3-way merge Markdown with diffy 0.5.2 and fall back to a conflict copy, card-level last-writer-wins for Kanban JSON, and a persisted offline queue. Effort estimate (ASSUMED, solo dev): Mode 1 ~1 week; Mode 2 core ~3–4 weeks + ~2 weeks per provider + verification lead times. Strong recommendation: ship Mode 1 first; Mode 2 only if the owner accepts shipping OAuth client credentials and ~2 months of work.

### F2. Dataless (cloud-only) file detection: SF_DATALESS flag; old st_blocks heuristic agrees  [verified]
SDK header /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/stat.h:359 defines SF_DATALESS 0x40000000. Two real dataless files in the OneDrive folder show st_flags=0x40000060, size>0, blocks=0; materialized files show flags 0x40 with blocks>0. Old novalis is_cloud_placeholder (len>0 && blocks==0, crates/novalis-core/src/vault/fs.rs:30-33) classified both correctly. Rust: std::os::macos::fs::MetadataExt::st_flags() exists (compiled with rustc 1.96.0). TN3150: 'call stat or getattrlist and examine if SF_DATALESS is present in stat.st_flags'; stat/getattrlist materialize dataless intermediate FOLDERS; directory enumeration and fileExists materialize folders. Verified locally: stat on a dataless file did NOT materialize it (still dataless after).
_evidence: scratchpad/dataless_test.c and stflags.rs runs; https://developer.apple.com/tutorials/data/documentation/technotes/tn3150-getting-ready-for-data-less-files.json_

### F3. Preventing downloads: setiopolicy_np OFF makes read() return EDEADLK; libc crate lacks the symbol  [verified]
setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES=3, IOPOL_SCOPE_THREAD=1, IOPOL_MATERIALIZE_DATALESS_FILES_OFF=1) returned 0; then open(O_RDONLY) succeeded but read() failed errno 11 (EDEADLK, 'Resource deadlock avoided') and the file stayed dataless (no 11.7 MB / 50 MB download). Policy is per-thread (or process). libc 0.2.189 (cached in ~/.cargo) has no setiopolicy_np or IOPOL_* constants — declare extern "C" { fn setiopolicy_np(i32,i32,i32)->i32 } (verified compile+run). Old novalis NEVER set this policy; it only skipped placeholders by heuristic — any accidental read hydrated. The new scanner thread should set OFF and treat EDEADLK as 'cloud-only'.
_evidence: scratchpad runs; /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/resource.h:509,520-521,540-541; grep of ~/.cargo/registry/src/*/libc-0.2.189/src/unix/bsd/apple/_

### F5. Conflict-copy naming per vendor (OneDrive consistent across sources; Google Drive desktop unverified)  [likely]

No official Microsoft page describing the suffix was found (support article 'Why has my filename changed' only covers invalid chars/truncation). Google Drive for desktop: community reports '(1)' suffix and names containing 'conflict'/'conflicted copy' plus a sync_log.log; no official Google doc found — treat as ASSUMED.

### F6. File watching inside CloudStorage: no authoritative statement; treat FSEvents as hint, scan as truth  [assumed]
No Apple doc found stating FSEvents semantics for File Provider domains. Reasoning: fileproviderd itself consumes FSEvents and provider-applied remote changes are ordinary APFS writes, so events should arrive; hydrate/evict transitions likely surface as attribute/modify events; initial-sync bursts are possible. notify crate: stable 8.2.0 (2025-08-03), 9.0.0-rc.5 prerelease (2026-08-30); old novalis used notify 8 + notify-debouncer-mini 0.7 with 300 ms debounce and an is_recent_self_write filter (apps/desktop/src-tauri/src/watcher.rs). Recommendation: keep watcher + stat-only reconciliation scan on launch/focus (old walk_note_metadata pattern).
_evidence: ASSUMED (reasoning); https://crates.io/api/v1/crates/notify; old watcher.rs_

### F7. Atomic save (temp+rename) in File Provider folders: not shown to break; keep temps hidden, hold no locks  [assumed]
No verified source that write-temp-then-rename breaks OneDrive/Drive File Provider domains; NSDocument/TextEdit do exactly this and TN3150 recommends NSDocument. Weak counter-evidence: MS Q&A anecdote that creating brand-new files in online-only OneDrive folders sometimes fails while replacing existing files succeeds (Excel VBA). Practical risks: rename creates a new inode → provider may see delete+create (server version history may not chain); temp names visible to the vendor client unless hidden. Design: same-directory dot-prefixed temp (.name.md.tmp-<rand>), fsync, rename, close immediately; never flock/O_EXLOCK; never keep long-lived fds; record (size, mtime) after own write to suppress echo events.
_evidence: https://learn.microsoft.com/en-ie/answers/questions/2285303/...; TN3150; ASSUMED for rename-breaks claim (unconfirmed either way)_

### F8. Google OAuth for desktop: loopback 127.0.0.1, PKCE, refresh tokens always issued, client_secret effectively required for 'Desktop app' clients  [verified]
Google native-app doc: redirect 'http://127.0.0.1:port' (localhost allowed but 'may cause issues with client firewalls'); custom URI schemes 'no longer supported'; PKCE S256 with 43–128 char verifier; 'refresh tokens are always returned for installed applications'; token endpoint https://oauth2.googleapis.com/token; 'it is assumed that these apps cannot keep secrets' and installed-app docs say 'the client secret is obviously not treated as a secret'. Cloud Console auto-generates a secret for Desktop-app clients and community threads (2025–2026) report invalid_request on code exchange without client_secret even with PKCE → plan to send it. Old novalis oauth.rs (479 lines, verified) already implements loopback+PKCE+state+keychain and only lacks the client_secret param; it read NOVALIS_GOOGLE_CLIENT_ID from env or a user-pasted id stored in keychain (set_client_id).

### F11. Google Drive v3 has NO etag / If-Match; conflict control must use 'version' + checksums  [verified]
Discovery doc (revision 20260901, downloaded via curl): File schema has no 'etag' field; no 'etagRequired' anywhere; files.update params: addParents, removeParents, keepRevisionForever, useContentAsIndexableText, supportsAllDrives, includeLabels, ocrLanguage. Present: version ('monotonically increasing ... reflects every change made to the file on the server'), headRevisionId, md5Checksum, sha1Checksum, sha256Checksum (output only, binary content only), modifiedTime (client-settable), appProperties (124 bytes key+value, ≤30 per app), parents (single parent only), name ('isn't necessarily unique within a folder'). Optimistic write = GET fields=version,sha256Checksum → compare with stored → PATCH; a small race window remains (no server-side precondition). files.generateIds (count ≤1000) gives idempotent creates.
_evidence: scratchpad/drive_v3.json analysis; https://developers.google.com/workspace/drive/api/reference/rest/v3/files; https://developers.google.com/workspace/drive/api/guides/properties_

### F17. Graph delta API semantics  [verified]
GET /me/drive/root/delta → pages via @odata.nextLink, ends with @odata.deltaLink; deleted items carry a 'deleted' facet; 'you should only delete a folder locally if it is empty after syncing all the changes'; feed shows latest state per item, an item may appear multiple times (use last); parentReference.path is omitted and folder renames do not re-list descendants → 'always track items by id'; ?token=latest returns an empty page + fresh deltaLink; HTTP 410 Gone with resyncChangesApplyDifferences (replace local with server, upload unknown local) or resyncChangesUploadDifferences (upload differing files, keep both copies if unsure) and a Location header starting a fresh enumeration; consumer OneDrive delta omits ctag and size on deletes; timestamp tokens are OneDrive-for-Business only; delta with token costs 1 resource unit.

### F18. Graph uploads, preconditions, conflict behavior, hashes  [verified]
PUT /me/drive/items/{id}/content or /root:/path:/content up to 250 MB (page updated 2026-08-11; older docs said 4 MB). createUploadSession: If-Match / If-None-Match with eTag or cTag → 412 Precondition Failed; body item '@microsoft.graph.conflictBehavior': fail (default) | replace | rename, deferCommit; fragments must be multiples of 320 KiB (327,680 B), <60 MiB per request, 5–10 MiB recommended, sequential; 202 with nextExpectedRanges; GET uploadUrl to resume; 404 → restart; 409 nameAlreadyExists on commit; expiration extended per fragment. driveItem: eTag = metadata+content, cTag = content only (not returned for folders in ODB); fileSystemInfo is read-write (client can set lastModifiedDateTime). Hashes: quickXorHash is 'the only value that is guaranteed to be available for both OneDrive for work or school and OneDrive for home'; sha1Hash/crc32Hash 'if available'; sha256Hash 'isn't supported'. The v1.0 simple-PUT page does not list If-Match (the older OneDrive-API page did) → use createUploadSession+If-Match for every write to get a real compare-and-swap.
_evidence: https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0; https://learn.microsoft.com/en-us/graph/api/resources/driveitem?view=graph-rest-1.0; https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0_

### F22. Vendor path/name rule mismatches that a sync engine must sanitize  [likely]
OneDrive client rewrites invalid characters (* # " : < > ? / \ |) to underscores and truncates over-long paths (official support page); OneDrive names are case-insensitive (ASSUMED, standard behavior). Google Drive allows arbitrary names including '/' and duplicate names in one folder (verified 'isn't necessarily unique'); APFS is case-insensitive by default on Macs. Consequence: keep an explicit remote_id↔path map, detect case-only collisions and duplicate remote names, and normalize Unicode (NFC) before comparing paths.

## RECOMMENDATIONS

### R1. Ship MODE 1 (vault inside the vendor's CloudStorage folder) first and make it the default sync story for both Google Drive and OneDrive.
Zero OAuth, zero verification, zero shipped credentials, ~1 week of work, and most of the code existed in old novalis (placeholder-aware scan, conflict-copy detector/resolver, watcher with self-write suppression). Required hardening: (1) detect File Provider domains via ~/Library/CloudStorage prefix or xattr com.apple.file-provider-domain-id and show a one-line hint; (2) run the scanner thread with setiopolicy_np(3,1,1) and treat EDEADLK/SF_DATALESS as cloud_only; (3) open notes off the main thread with a timeout (materialization can take seconds); (4) keep index/cache/sync state in the app data dir, never in the vault; (5) generalize the conflict-copy regex to '<stem>-<hostname>.md', '<stem> (n).md', "<stem> (... conflicted copy ...).md" and require differing content; (6) write via same-dir hidden temp + fsync + rename, close fds immediately, never lock.
_rejected: Starting with Mode 2 (2 months, credentials in binary, verification lead times); disabling the watcher and scanning only (misses live remote edits)._

### R2. If MODE 2 is built: Google via drive.file only, OneDrive via Files.ReadWrite.AppFolder (approot) — one app-owned root folder per provider, never a user-chosen arbitrary folder.
drive.file is non-sensitive (no CASA, no 100-user cap, no 7-day token expiry once published) and approot is least-privilege with a constant path; both give a fixed remote root so path↔id mapping is simple. Full 'drive' scope would cost ~$540–$4,500/year in annual assessments for a minimal open-source tool.
_rejected: Full drive / Files.ReadWrite.All (restricted or scarier consent, assessment cost); drive.appdata (hidden, unusable by other tools/agents)._

### R3. Mode 2 engine: SQLite state DB in app data dir + content-addressed base blobs; hash-driven 3-way planning lifted from novalis_core::sync::manifest; version-token preconditions per provider.
Schema: files(path PK, size, mtime_ns, local_hash, base_hash, remote_id, remote_version [Drive: version int64; Graph: cTag], remote_hash [Drive: sha256/md5; Graph: quickXorHash], parent_remote_id, state ∈ {clean, dirty_local, dirty_remote, conflict, pending_upload, pending_delete, tombstone}, last_error), remote_ids(remote_id PK → path) for id-based rename tracking, cursor(provider → startPageToken/deltaLink), queue(op, path, attempts, next_retry, session_url). Base blobs stored as blobs/<sha256> so 3-way merge has an ancestor; prune unreferenced. Change detection: notify debounced 300–500 ms (self-write suppression by expected size+mtime) plus a stat-only full scan on launch/focus/every 10 min; hash only when size or mtime differ. Remote detection: poll delta every 60 s while focused and right after each own upload (no webhooks — both vendors need a public HTTPS endpoint). Cycle per path uses the old plan() table: local-only change → upload with precondition (Drive: re-GET version must equal stored; Graph: If-Match cTag); remote-only → download, verify hash, write via temp+rename, update base; both → merge policy; deletes: local delete + remote unchanged → remote trash (Drive files.update trashed=true; Graph DELETE → recycle bin); remote delete + local unchanged → move local file to the app's trash, never hard-delete; delete-vs-edit → keep the file and re-upload (resurrect), flag it.
_rejected: mtime-based decisions (clock skew, vendor mtime rewriting); manifest-file-on-server designs (extra write per sync, itself a conflict source); Drive appProperties as the path store (124-byte cap, 30 props)._

### R4. Conflict policy for Markdown: automatic 3-way merge (diffy::merge with the stored base blob) when it applies cleanly; otherwise keep the local file untouched and write the remote version as '<name> (conflict <device> <YYYY-MM-DD HHMM>).md' next to it, then continue syncing. No blocking dialogs, no manual merge UI in v1.
Notes edited on two devices offline are the common case; clean merges (different paragraphs) converge silently, true overlaps surface as a visible file the existing conflict detector already recognizes. Deterministic and unit-testable against an in-memory fake provider. Last-writer-wins silently loses text; always-copy is noisy.
_rejected: Last-writer-wins (data loss); conflict copies only (noisy); CRDT/OT (far beyond minimal)._

### R5. Kanban data: one JSON file per board (kanban/<board-id>.json) with cards keyed by id and per-card updated_at; merge by card-level last-writer-wins with tombstones, columns merged by 3-way list merge; sorted keys, pretty-printed. Never produce a conflict copy for Kanban files.
Small structured files merge deterministically without user involvement; ordering conflicts are cosmetic. Per-card LWW on a device-local timestamp is the only place clock skew matters, and the damage is bounded to one card. Keeps Kanban content outside notes as the brief demands and lets Mode 1 vendor sync carry the same files.
_rejected: One file per card (hundreds of requests per board on Mode 2); binary/SQLite board (unmergeable, opaque to agents); LWW on the whole board file (loses cards)._

### R6. Renames/moves: detect locally as (vanished path, new path with identical hash) within one scan/debounce window and issue a provider move (Graph PATCH parentReference/name; Drive files.update name/addParents/removeParents); apply remote renames by remote_id. Handle case-only renames and NFC/NFD by normalizing before comparison; refuse to create two local files that differ only by case (flag instead).
Preserves remote ids and version history and avoids re-uploading whole files; Graph delta only makes sense when tracking by id. APFS case-insensitivity plus Drive's permissive naming otherwise produces silent overwrites.
_rejected: Treating renames as delete+create (history loss, double traffic, delete-vs-edit ambiguity)._

### R7. Offline queue and failure handling: persist every remote op in the queue table; exponential backoff with jitter, honor Retry-After on 429/503 (Graph) and back off on 403 userRateLimitExceeded/429 (Drive); persist resumable/upload-session URLs and resume via status query; verify every upload against the server hash (Drive sha256/md5; Graph quickXorHash) before marking clean; on Graph 410 follow resyncChangesApplyDifferences/UploadDifferences literally; on invalid_grant/401 enter a 'reconnect' state that keeps the queue; skip files above a fixed size cap and log loudly.
These are the documented failure modes of both APIs (session expiry, 404 on lost session, 410 resync, rotated refresh tokens, throttling). Verifying by hash makes partial uploads and clock skew irrelevant. A visible size cap avoids surprising multi-GB attachments in a Markdown vault.
_rejected: Retry-forever loops (throttled requests count against quota); trusting timestamps._

### R8. OAuth client credentials: ship the Google client_id AND its (non-secret by Google's definition) client_secret in the binary, plus keep the old novalis 'paste your own client id' escape hatch; ship the Microsoft client_id (no secret). Register the Microsoft app in a work/school tenant so publisher verification stays possible.
Google Desktop-type clients in practice require client_secret at token exchange; Google's docs explicitly accept embedding it. The escape hatch lets power users avoid shared-quota risk. Microsoft public clients need no secret; apps registered with a personal Microsoft account can never be publisher-verified.
_rejected: Env-var-only client ids (unreachable for Finder-launched apps, as old novalis noted); a hosted token-exchange backend (server to run, against 'minimal')._

### R9. Effort plan (ASSUMED, solo dev): Mode 1 ≈ 1 week. Mode 2 core (state DB, scanner, planner+merge, queue, fake-provider tests) ≈ 3–4 weeks; Google provider ≈ 1.5–2 weeks + Cloud Console brand verification wait; OneDrive provider ≈ 1.5 weeks + optional Partner Center enrollment; real-account soak testing ≈ 1 week. Build OneDrive before Google if only one provider fits the schedule.
Graph offers real preconditions (If-Match/412), reliable delta with documented resync, and a guaranteed hash; Drive lacks etags and needs the client_secret question settled. Both providers share the OAuth loopback code already written in old novalis.
_rejected: Using third-party high-level SDK crates (google-drive3/yup-oauth2, msgraph) — heavy dependency trees for a handful of endpoints; raw reqwest calls are ~10 endpoints per provider._

## OWNER DECISIONS
- Ship Mode 2 (in-app login) at all in v1, or Mode 1 only? Mode 2 is roughly two months of work plus vendor verification lead times; Mode 1 covers both vendors in about a week.
- Accept shipping Google OAuth client_id + client_secret inside the open-source binary (Google-sanctioned for installed apps, but enables quota abuse/impersonation)? Alternatively require users to paste their own client (old novalis approach) — or offer both.
- Google scope: drive.file (only the app-created vault folder is visible; files the user drops into it via the web UI may be invisible to the app until opened/created by it) vs full 'drive' (restricted scope, annual CASA ~$540–$4,500).
- OneDrive scope: Files.ReadWrite.AppFolder (fixed 'Apps/<app name>' folder, least privilege) vs Files.ReadWrite (user picks any folder, broader consent).
- Microsoft publisher verification: create a Partner Center (CPP) account and a work/school tenant so work-account users in step-up-consent tenants can consent, or target personal Microsoft accounts only at first?
- Conflict policy: auto 3-way merge + conflict copy on overlap (recommended) vs conflict copies only vs last-writer-wins.
- Kanban file layout and merge rule: one JSON per board with card-level last-writer-wins (recommended) vs one file per card.
- Delete propagation: automatically trash remotely/locally on the other side (recommended, always to a recoverable trash) vs ask.
- Fixed defaults with no settings: poll interval (proposed 60 s while focused, none in background), size cap for synced files (proposed 25 MB), remote root folder name (proposed 'novalis'). Confirm these are hard-coded rather than settings.
- Mode 1 UX: how loud should the 'this vault is in a cloud folder / cloud-only notes / conflict copies detected' hints be (one-line banner vs status-bar icon)?
- Should the CLI/agent tool be allowed to trigger a sync or read sync state, and may it write into the vault while a Mode 2 sync is running (needs the same self-write suppression)?
