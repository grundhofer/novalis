

# CRITIC
The plan covers every requirement of the brief (monorepo, Mac first, Sublime-like editor + file types, Kanban outside notes, both sync modes, designSprache, de/en, empty branch, agent CLI) and its minimalism gate is real. Three things would change what the owner decides or the developer builds: (1) §4 converts the brief's "ASK before adding" into opt-out defaults for about a dozen additions and never defines which rows are "needs yes"; (2) §4.3 rejects split view while §4.4/§12 build a board+note split, so the pane model is decided both ways; (3) the roadmap ships a 20-command CLI with golden tests as the first product exit criterion before any desktop UI, although the brief says to start with the desktop app. Below those: a `Cmd-B` shortcut collision copied from two reports, a day-1 git command that fails as written, a handful of features shipped without a §4 row, undefined alias semantics, and an undecided settings UI. No data-loss risk was found in the brief-compliance lens.

## [high] F1 — §4 intro, §4.1, §4.3 vs §0 (Notes row), §7.1, §14
**Claim:** The plan turns the brief's "ASK before adding any setting or feature" into an opt-out: additions beyond the brief ship if the owner says nothing, and the set of rows that actually require an explicit yes is never defined.
**Evidence:** §4: "Each item has a default the plan assumes if you say nothing; 'needs yes' items ship only with an explicit yes recorded in an ADR" — but no row is labelled 'needs yes'; the only visible distinction is bold ("**yes, v1**") vs plain ("yes (zero cost)", "yes"), unexplained. §4.3 header says "default **no** unless marked", then marks 12 additions yes (preview v1.1, backlinks, tags filter, [[/# completion, tombstones, several boards, Flat 2.0 row, relink, meta, init, help --json/skill, en-XA). §4.1: "the plan assumes all four" vs §0: "Each of the four still needs your yes". §0 Notes row already lists "tags, backlinks" as the decided minimal set while §4.3 lists the same as beyond-brief needing yes and §14 lists them as the first cut. Research critique R11 recommended "each item with a default 'no'" (docs/research/2026-09-05-critique.md line 184).
**Fix:** Rewrite §4 so that silence never ships an addition: every row that adds a setting, feature, command, dependency or mockup is 'needs yes' (drop the 'default the plan assumes' sentence); keep 'no' as the only allowed default; remove backlinks/tags/completion from the §0 Notes row and mark them 'pending yes' in §7.1; add a 'Recommended' column instead of pre-filled yes so the recommendation stays visible without becoming the decision.

## [high] F2 — §4.3 (Split view row) vs §4.4 (Card click), §4.5 item 3, §6.3 L5, §12 Phase 3
**Claim:** The plan rejects split view for the editor and simultaneously builds a two-pane board+note split, so the pane-focus model is decided both ways.
**Evidence:** §4.3: "Split view (two panes) | editor-scope | no | Adds a pane-focus model". §4.4 default: "Card click | **Opens the linked note in a split next to the board** (mockup L5)". §12 Phase 3 builds "Kanban pane with drag and drop, column editing, note linking, board + note split". **Fix:** Make it one decision in §4.4: either (a) v1 has no pane model — card click opens the note in a tab and `Cmd-\`-style toggle returns to the board (drop L5 from Phase 3, keep it as a mockup only), or (b) v1 has a two-pane model, in which case the §4.3 split-view row becomes the same feature and is asked once. Default should be (a) to match the §4.3 'no'.
