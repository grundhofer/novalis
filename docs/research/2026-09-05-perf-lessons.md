TOOLS: Local read-only tools (Bash: find/wc/grep/sed/stat/gzip/git; Read) were used for all code, bundle and git-history measurements. WebSearch and WebFetch were available after loading via ToolSearch and were used for three searches (tiptap-markdown round-trip issues; notify-debouncer-full vs mini; macOS SF_DATALESS / File Provider) and one fetch (tiptap-markdown README maintenance statement). No files were modified. Not verified: absolute latency numbers of the old app (no benchmark exists; no profiling was run), RSS/memory of the old app, File Provider behavior of temp+rename saves on real OneDrive/Google Drive folders, and exact library versions for the rewrite (deliberately not proposed).

## SUMMARY
Old novalis (488 commits, 2026-05-24 → 2026-08-18) grew from a notes app into a notes+tasks+calendar+AI+P2P-sync+voice+PDF+canvas+plugins platform in 86 days, and its weight is structural, not incidental. Frontend: 135 source files / 29,975 LOC, 79 component files (Sidebar 1,569 LOC, EditorPane 1,256), 15 zustand stores (vaultStore 1,362 LOC), a generated IPC surface of 158 commands + 9 events, 666 npm packages in the lockfile, and an 8.2 MB dist in which the eager modulepreload set is 4.63 MB raw / 1.30 MB gzip — including a 3.09 MB mermaid chunk that is `import()`-ed lazily in source but statically referenced by the chunk that holds the TipTap editor, plus all four i18n locales bundled eagerly and 1.29 MB of fonts. Core: 28,206 LOC Rust in novalis-core (index alone 7,978 LOC across 9 tables + FTS5 + HNSW vectors + entity graph), 11,183 LOC in the Tauri shell, 910 Cargo packages, a 38 MB stripped/LTO release binary (whisper-rs, fastembed/ONNX, iroh, vendored libgit2+openssl). Startup is gated behind the index: the Tauri setup thread opens the last vault, runs the mtime scan, then calls `stats::vault_info` which re-reads every note body, and only then sets engine state — meanwhile `currentVault()` returns None so the frontend renders the vault-picker until `reindexed-event`, after which it needs 3 more sequential IPCs (currentVault → getPreferences → getFolderTree) before the tree paints; ≥12 IPC calls fire at boot in total. The single `Mutex<Option<Engine>>` serializes every command, the watcher's per-event reindex, and the git autocommitter on one SQLite connection. Every autosave (200 ms serialize debounce + 600 ms autosave debounce) serializes the whole ProseMirror doc to Markdown, re-parses and re-serializes the entire YAML frontmatter via serde_yaml to stamp `modified:`, does an fsync'd temp+rename write, reads the file back twice, and re-indexes the note. The editor's Markdown→ProseMirror→Markdown round trip through the now-unmaintained `tiptap-markdown` package produced five separate silent-corruption bugs (wikilink/math/angle-bracket escaping 5a7cbcb, tables flattened 11b9d50, one Enter → table replaced by "[table]" ed830e4, non-mapping frontmatter → first section deleted 887d424, pipe in cell shreds table 887d424) plus nine documented lossy normalizations; the last two shipped in v0.2.1-rc1 despite 629 Rust + ~551 JS tests. Watcher: notify-debouncer-mini 300 ms, one event per file with no batching; each external `note-changed` triggers a full tree refetch (recursive read_dir) plus a task reload on the frontend, and echo suppression is a 2 s wall-clock window. Cloud-only detection is a `st_blocks == 0` heuristic rather than the documented `SF_DATALESS` flag. The rewrite must invert these defaults: tree from directory enumeration, index strictly background and optional, one IPC per user action, text buffer as the source of truth with identity serialization, never rewrite untouched frontmatter, atomic writes with content-hash echo suppression, batched watcher diffs, no global lock, and a CI-enforced bundle/IPC budget.

### F11. Cloud-only (dataless) detection uses a `st_blocks == 0` heuristic instead of the documented SF_DATALESS flag; non-unix always false  [verified]
vault/fs.rs:30-38: `is_cloud_placeholder(meta) = meta.len() > 0 && meta.blocks() == 0` on unix, `false` elsewhere. Comment admits it is a heuristic ('On APFS even a 1-byte materialized file occupies a block'). Empty placeholder files (len==0) are read as normal. The documented signal per Apple/Eclectic Light/Michael Tsai: `SF_DATALESS` (0x40000000) in `stat.st_flags`, a synthetic read-only kernel flag; File Provider (iCloud, OneDrive, Google Drive on macOS 12.3+) materializes on read and can also set SF_DATALESS on DIRECTORIES so enumeration itself can trigger materialization (fish-shell #8399: `**` glob materializes dataless dirs). Old code also indexes placeholders with empty bodies and relies on cloud_only=1 rows to force re-read later because 'a cloud sync hydrates a file's contents WITHOUT bumping its mtime'.
_evidence: crates/novalis-core/src/vault/fs.rs:20-38; index/search.rs:260-275; WebSearch results: https://mjtsai.com/blog/2023/05/11/getting-ready-for-dataless-files/, https://eclecticlight.co/2026/05/09/explainer-file-provider-and-cloud-services/, https://github.com/fish-shell/fish-shell/issues/8399, https://gist.github.com/lijunle/b458c1f91c32066466057bc80f6d80fc_

### F13. Data-loss window during live typing (d7d7406) and the flush-registry machinery it required  [verified]

### F14. Truncating writes shipped for 6 weeks; atomic write added 2026-07-06  [verified]

## RECOMMENDATIONS

### R1. PERFORMANCE BUDGET (CI-enforced numbers for the rewrite): (1) Window visible ≤ 150 ms after process start; file tree interactive ≤ 300 ms after webview ready on a 10k-note vault (warm disk), independent of any index. (2) Eager JS ≤ 250 KB gzip total, no single eager chunk > 120 KB gzip, eager CSS ≤ 20 KB, fonts 0 bytes bundled (system font) or ≤ 60 KB if the chosen style demands one; CI asserts the dist/index.html modulepreload list against an allowlist. (3) IPC at boot ≤ 3 calls before the tree paints (ideally 1 `bootstrap` returning {vaultPath, tree, lastOpen}) and ≤ 5 total; 1 call to open a note; 1 call to save. (4) Open note: 100 KB file ≤ 16 ms p95 end-to-end, 1 MB ≤ 60 ms. (5) Keystroke → paint ≤ 8 ms p95 in a 1 MB document; no work proportional to document size per keystroke. (6) Save: exactly 1 fsync'd write, 0 re-reads, 0 index work on the calling path; autosave debounce 500-1000 ms plus flush on blur/tab-switch/quit (owner decides autosave vs explicit save). (7) Index (if it exists): stat-only incremental scan of 10k notes ≤ 1.5 s; full rebuild of 10k notes / 100 MB ≤ 10 s; runs on its own thread with its own connection; search results available progressively. (8) Watcher: 100 ms debounce, one batched diff per window; 1,000-file sync burst causes ≤ 1 tree update and ≤ 100 ms of UI-thread work. (9) Idle RSS ≤ 150 MB (Rust + webview) — ASSUMED target, old app unmeasured. (10) Release binary ≤ 12 MB stripped; ≤ 60 npm packages and ≤ 200 Cargo packages in lockfiles. (11) Large-vault fixture (generated 10k and 50k notes, some 2 MB files, deep folders) with a benchmark job from the first commit.
Old app: eager set 1.30 MB gzip (mermaid 814 KB alone), 4 sequential IPCs + full index scan + full re-read of every note before first tree paint, ≥12 boot IPCs, 3 disk reads + 1 fsync + YAML rewrite + reindex per 600 ms autosave, 38 MB binary, 666 npm / 910 cargo packages, and every perf fix in history landed after users felt lag on a 63-note demo vault.
_rejected: Budgets without CI enforcement (old vite.config had correct intent comments that the build silently violated); budgets relative to the old app (they should be absolute)._

### R2. RULE 1 — Render the file tree from directory enumeration only; the index is never on the path to first paint. `bootstrap` reads the last vault path from a tiny settings file, enumerates directories on a thread (stat only, respecting SF_DATALESS on dirs), streams the tree, and shows it. Titles come from filenames; if a title-from-frontmatter feature is wanted later it must be lazy and per-visible-row.
Old get_folder_tree needed index summaries + a recursive walk; open_vault_impl ran the mtime scan AND stats::vault_info (reads every note) before setting engine state; the UI showed the vault picker until reindexed-event (lib.rs:384-388, commands.rs open_vault_impl, stats.rs:12-34, App.tsx:428).

### R3. RULE 2 — The editor's source of truth is the text buffer; serialization is the identity function. Use a code-editor model (CodeMirror 6 with Markdown language + decorations/live preview) rather than a ProseMirror/TipTap schema; never load Markdown into an AST and write the AST back. Any 'rich' rendering is a decoration over the unchanged text. If the owner insists on WYSIWYG, it must be an explicit, separate, opt-in mode that writes back only edited ranges — and that is a feature that needs an owner decision.
Five silent-corruption bugs (5a7cbcb, 11b9d50, ed830e4, 887d424 ×2) and nine documented lossy normalizations all stem from markdown→ProseMirror→markdown; tiptap-markdown is unmaintained per its README; the 200 ms full-doc serialize + 600 ms autosave created the d7d7406 typing data-loss window and ~150 LOC of flush-registry machinery. Brief explicitly asks for a 'clean, high-performance text editor like Sublime'.
_rejected: Official @tiptap/markdown (still an AST round-trip; still normalizes); Milkdown/remark-based editors (same class of problem); keeping TipTap with more custom serializers (old app already had MarkdownText + MarkdownTable overrides and still shipped two deletions in rc1)._

### R4. RULE 3 — Never rewrite bytes the user did not edit. No `modified:` stamping, no frontmatter re-serialization, no whitespace/line-ending normalization on save. Metadata the app needs (mtime, size) comes from the filesystem. If frontmatter editing is ever added, it edits the YAML text range in place (string surgery), not a typed struct.
update_modified re-emits the entire YAML block via serde_yaml on every autosave (order/comments/quoting lost, alphabetical extras) and was the exact code path that deleted a user's first section in 887d424; per-autosave `modified:` bumps also force cloud clients to re-upload every 600 ms of typing.

### R5. RULE 4 — Atomic, verified saves: write `.<name>.<rand>.tmp` in the same directory, fsync the file, rename over the target, fsync the parent directory; before writing, compare the target's current (mtime, size, content-hash-of-last-known) with what the editor loaded — if it changed underneath, refuse and surface a conflict instead of overwriting. Record (path, size, mtime, blake3/xxhash of written bytes) in a self-write table so watcher echoes are matched by content, not by a 2 s clock. Verify on real OneDrive and Google Drive folders (File Provider) that temp+rename does not create conflict copies or drop xattrs — this is an explicit test task, not an assumption.
6469e39 shows 6 weeks of truncating writes; write_atomic today skips the directory fsync; echo suppression is a wall-clock window that misses task and wikilink commands (004c8a5); the external-change check reads the file again and compares strings (vaultStore.handleExternalChange).

### R6. RULE 5 — Watcher: notify-debouncer-full (rename stitching via FS IDs) at 100 ms, coalesce all events in a window into ONE batch {added, removed, modified, renamed} delivered as ONE Tauri event; the frontend applies the batch to its in-memory tree (no refetch). Ignore dot-files, `*.tmp`, `~*`, editor lock files, `.novalis/`. Cloud conflict-copy detection is a filename filter on the batch, not a full WalkDir. Vault-wide rescans (folder move, external mass change) are throttled and run on the indexer thread only.
Old watcher emitted one note-changed per file and the frontend responded to each with getFolderTree (recursive read_dir) + listTasks + getPreferences; only conflict scanning was coalesced; listConflicts walks the whole vault with 3 regexes per file at every boot.

### R7. RULE 6 — No global lock. The Rust side has (a) a vault service that only does filesystem calls and holds no long-lived state beyond the vault path, and (b) an optional indexer actor owning its own SQLite writer connection plus a small read pool; commands that don't need the index never touch it. Long operations (rebuild, mass move) are jobs with progress events, cancellable on vault switch.
AppEngine(Mutex<Option<Engine>>) serialized every command, the watcher's per-event reindex, and autocommit; busy_timeout 5 s and WAL were added after 'database is locked'; a8b21ce had to move three main-thread-blocking commands (one blocked up to 180 s).

### R8. RULE 7 — Never read a cloud-only file eagerly. Detect dataless files/dirs via `st_flags & SF_DATALESS` on macOS (fallback: blocks==0 && len>0), show them in the tree with a cloud badge, and only read on explicit open (with a visible 'downloading…' state and a cancellable timeout). Enumerate directories with a method that does not trigger materialization (readdir + lstat only; no `canonicalize`, no `**` glob through dataless dirs). Index (if any) never indexes their bodies; it records them as 'unindexed'.
Old code's heuristic is blocks()==0 and non-unix returns false; incremental scan had to special-case cloud_only rows because hydration doesn't bump mtime; open_vault comments admit a cloud vault 'hydrates online-only files over the network — slow and blocking'. SF_DATALESS is the documented kernel flag; File Provider can mark directories dataless so even enumeration can hydrate (fish-shell #8399).

### R9. RULE 8 — One IPC per user action, batched boot. Commands: `bootstrap()`, `read_file(path) → {text, mtime, size, encoding}`, `write_file(path, text, expected_mtime)`, `list_dir(path)`, `rename`, `delete`, `search(query)` (streaming). No `getPreferences` from multiple stores; settings arrive in `bootstrap`. Bindings generated (tauri-specta is fine) but the surface must stay < 25 commands.
158 commands / 2,201-line bindings; getPreferences called 3× at boot from three stores; ≥12 boot round-trips; openNote → flushAll → getNote → separate backlinks/unlinkedMentions/listTags calls.

### R10. RULE 9 — Bundle discipline enforced by build: a CI step parses dist/index.html and fails if any modulepreload chunk exceeds the budget or is not on an allowlist; heavy renderers (math, diagrams, PDF, highlighting grammars) are excluded from v1 entirely unless the owner asks — and if added later they must be proven lazy by that CI check, not by a source-level `import()`. Ship de + en only, with the inactive catalog loaded lazily; no react-i18next + i18next-parser pipeline for a ~200-string app (a 2-key JSON per language and a 20-line `t()` suffice).
mermaid (3.09 MB raw) was `import()`-ed in source yet statically referenced by the editor chunk and preloaded at boot; 4 locales (448 KB source) bundled eagerly; 1.29 MB of fonts (Inter + 30 KaTeX faces) in dist; vite.config comments described a lazy split the build did not produce.

### R11. RULE 10 — Kanban and tasks are their own data (e.g. `.novalis/kanban/<board>.json` or a per-board Markdown-adjacent JSON in the vault so it syncs), referencing notes by relative path (+ optional stable id in frontmatter only if the owner accepts one key). The app never parses task tokens out of note bodies, never runs regexes over every note at index time, and never rewrites note text to update a card.
Old task index: 1,091 LOC, 11 regexes per note per reindex (cde9da7), tasks table with 17 columns rebuilt from note bodies, task edits done by rewriting note lines (tasks/index.rs write_lines). Brief mandates Kanban content lives OUTSIDE the notes.

### R12. RULE 11 — Settings: one small JSON in app-support (device-local) + at most a `.novalis/config.json` in the vault for per-vault choices; no prefs_version migrations, no feature-flag stamping on open, no per-vault preferences model of 763 LOC. Every new key requires the owner's explicit yes (per brief). No version history, trash, plugins, AI, voice, calendar, graph, canvas, PDF, P2P sync, git in v1 — not gated off, absent from the codebase.
Old app shipped every opt-in feature's code regardless of flag (README lists 7 opt-in groups; 13 settings panels; FeaturesPanel 582 LOC; open_vault ran ensure_features_stamp which may WRITE config and force a full rebuild on legacy vaults). The owner wants to be asked before any feature/setting.

### R13. RULE 12 — Startup does nothing but show the window and enumerate the vault. No migrations, no sweeps, no background threads except the watcher; no polling timers (old: 30 s reminder poll = 2 IPCs). Index/search, if present, is started only after the tree is interactive and is cancellable.
lib.rs setup(): synchronous voice sweep, trash migration, features stamp, asset scope, autocommit thread, watcher thread; App.tsx: 16 effects incl. runLaunchDigest + 30 s poll.

### R14. RULE 13 — Search: prefer on-demand search over a persistent index for v1 — a Rust ripgrep-style parallel scan (ignore crate + memchr/aho-corasick or `grep-searcher`) streaming results as they arrive; 10k notes / 100 MB is ~100 ms on Apple Silicon (ASSUMED, must be benchmarked). Add FTS5 only if the benchmark fails or the owner asks for ranked/fuzzy search; if added, it is an external-content FTS table (no duplicated bodies) owned by the indexer actor.
Old FTS5 table duplicated every note body, was one of 9 disposable tables plus vectors/entities, and dragged 7,978 LOC of index code; its schema-bump rebuild path forced full re-reads. The brief's 'wisdom organization' CLI can share the same scan library.
_rejected: Tantivy (heavier, another index to keep consistent); keeping FTS5 with content duplication._

### R15. RULE 14 — Test the failure modes that actually happened, from day one: a golden corpus asserting byte-identical save (write what was read, plus the edit, nothing else) across save→reopen→save ×3; a crash-during-write test (kill between temp write and rename); a watcher-burst test (1,000 files touched in 200 ms → 1 batch); a File Provider test on real OneDrive/Google Drive folders (manual checklist in the repo); and the generated 10k/50k-note benchmark in CI with the budget thresholds above.
887d424: 'Neither is visible to the 546 automated tests… both need a save-reopen-save cycle'; the round-trip corpus only pinned fixtures someone thought of; no perf fixture existed (demo vault 63 notes).

### R16. Cloud sync strategy for v1: use the local OneDrive / Google Drive folder (File Provider) as the vault and make the app File-Provider-safe (Rules 4, 5, 7) rather than building in-app OAuth clients. In-app login is a large surface (OAuth verification, token storage, delta APIs, conflict resolution) and the old repo already carried oauth.rs 479 LOC + keyring + 3 branches of OAuth fixes (fix/oauth-client-id) for calendar alone — flag as needs owner decision.
Minimal-by-default brief; local-folder sync reuses the provider's own conflict handling and version history; the old app's cloud-specific bugs were all in the local-folder path (placeholders, echoes, conflict copies) and are solvable with the rules above.
_rejected: Google Drive/OneDrive REST clients in v1 (owner may still choose this; then it should be a separate crate behind the same vault-service trait, added later)._

## OWNER DECISIONS
- Editor engine: accept a text-buffer editor (CodeMirror 6, Markdown syntax highlighting + optional live-preview decorations) with NO WYSIWYG for v1? The evidence says WYSIWYG round-tripping is the single largest source of silent data loss; a hybrid 'preview pane' can be added later without touching the save path.
- Autosave vs explicit save (Sublime-style dirty marker + Cmd+S, with autosave only on blur/quit)? If autosave: debounce value (500–1000 ms) and whether it may run while the window is unfocused.
- May the app write anything into notes it did not edit — specifically a `modified:` timestamp or a stable id in frontmatter (needed only if Kanban cards should survive note renames)? Recommendation: no writes; link cards by relative path and repair on rename via the watcher's rename batch.
- Search in v1: on-demand grep-style scan only (no index files anywhere) versus a background SQLite FTS index stored in app-support? The benchmark on the 10k-note fixture should decide, but the owner must accept that 'no index' means no ranked/fuzzy search initially.
- Cloud-only (dataless) files: show them in the tree with a badge and download on open, or hide them until the provider materializes them?
- Cloud sync: local OneDrive/Google Drive folder as vault (recommended for v1) versus in-app OAuth login to Drive/OneDrive APIs — and if the latter, is it acceptable as a v2 item?
- Font: system font (0 bytes, fastest) versus a bundled variable font (~50–100 KB) required by the chosen designsprache style?
- Languages: ship only de + en (drop fr/es from the old app)?
- Kanban storage format and location: JSON per board inside the vault under `.novalis/` (syncs with the vault) versus in app-support (device-local)? And what a card may reference (note path only, or path + heading anchor)?
- Which 'basic file types' the Sublime-like editor must open in v1 (e.g. .md, .txt, .json, .yaml, .toml, .csv, .js/.ts, .py, .rs, .sh, .html/.css) — each adds a highlighting grammar to the bundle budget.
- Version history / trash: none in v1 (rely on the cloud provider's own history and macOS Trash via `trash` crate)?
- Should the AI-agent CLI share the Rust vault/search library as a separate binary in the monorepo from v1, or come later?
